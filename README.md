# ClashIdFixer — экспорт коллизий Navisworks с исправленными Id

## Проблема

В составных объектах (Composite Object) Clash Detective находит коллизию на
уровне геометрии/подобъекта. При выгрузке результатов в XML в качестве Id
элемента попадает Id этого подобъекта, а не Id самого объекта (того самого,
у которого в свойствах Navisworks есть вкладка «Объект» — она появляется
только при «правильном» выборе, то есть на уровне Composite Object).

Плагин Signal при выгрузке параметров выгружает данные по «правильному»
выбору, то есть по Id объекта. В результате Id из выгрузки коллизий и Id из
выгрузки параметров Signal — это разные Id одного и того же элемента, и
связать их по ключу «имя файла + Id элемента» невозможно.

## Решение — вариант 1

Реализован отдельный плагин Navisworks 2022 (.NET API), который одной
кнопкой выполняет весь обязательный порядок действий и на лету подменяет
Id перед сохранением XML:

1. показать все элементы;
2. скрыть непроверяемые (по имени сохранённого набора / Sets);
3. обновить (пересчитать) все проверки Clash Detective;
4. выгрузить результаты всех проверок в XML;
5. для каждого из двух элементов коллизии — подняться от подобъекта
   геометрии вверх по дереву модели до объекта уровня «Composite Object»
   (это и есть «правильный выбор») и записать в XML именно его Id, а не Id
   исходного подобъекта.

Вариант 2 (патчить готовый XML отдельным скриптом-постобработчиком) в
итоге не потребовался — вся логика уместилась в одном плагине без
значительного усложнения, поэтому от варианта 2 отказались в пользу
цельного решения.

## Как определяется «правильный объект» (техническая суть)

У каждого `ModelItem` в Navisworks есть внутреннее (языконезависимое,
не переводится при русской локализации) свойство
`LcOaNode :: LcOaNodeIcon`, которое указывает тип узла дерева модели:
`File`, `Layer`, `Collection`, `Insert Group`, `Composite Object`,
`Geometry`. Коллизия всегда ссылается на узел `Geometry` (или иногда
`Insert Group`), а «правильный» выбор в интерфейсе Navisworks — это
ближайший родитель с типом `Composite Object`.

`ObjectResolver.ResolveObject()` поднимается от найденного в коллизии
элемента вверх по предкам (`ModelItem.AncestorsAndSelf`) и возвращает
первый узел, чей тип входит в список `ObjectNodeTypes` из конфигурации
(по умолчанию `Composite Object`, `Insert Group`). Это работает независимо
от того, откуда пришла модель — Revit, IFC, AutoCAD и т.п., — и независимо
от языка интерфейса Navisworks, потому что используется внутреннее имя
свойства, а не отображаемое.

Если подходящий предок не найден (в конфигурации отмечено `resolved="false"`),
в XML остаётся исходный подобъект — так строки, которые не удалось
исправить, видно сразу, а не молча теряются.

## Что попадает в XML

Для каждой коллизии выгружаются оба участвующих элемента, и для каждого:

- `SourceFile` — имя файла модели (для ключа «имя файла + Id»);
- `OriginalItem` — путь и тип исходного узла коллизии (для отладки);
- `ResolvedObject` — путь, тип и Id найденного «правильного» объекта:
  - `InstanceGuid` — собственный стабильный GUID объекта в Navisworks
    (`ModelItem.InstanceGuid`);
  - один или несколько `<Id source="Категория::Свойство">значение</Id>` —
    все совпавшие кандидаты Id (GUID/Element ID/Instance GUID/IFC GlobalId
    и т.п., см. `IdCandidates` в конфигурации).

Поскольку заранее неизвестно, какое именно поле использует Signal при
сопоставлении, экспортируются все найденные варианты — нужно один раз
посмотреть на реальный XML и на выгрузку Signal и выбрать, по какому полю
их сшивать (обычно это будет либо `InstanceGuid`, либо `Item::GUID`, либо
`Item::Element ID` — в зависимости от того, из чего сделана модель и что
именно читает Signal).

## Сборка

Проект — обычный (не SDK-style) `.csproj` под .NET Framework 4.8, как и
остальные плагины Navisworks 2022.

1. Откройте `src/ClashIdFixer/ClashIdFixer.csproj` в Visual Studio 2019/2022.
2. Единственная внешняя зависимость — `Autodesk.Navisworks.Api.dll` из
   вашей установки Navisworks Manage 2022. Путь к ней задаётся свойством
   `NavisworksInstallDir` в csproj (по умолчанию
   `C:\Program Files\Autodesk\Navisworks Manage 2022\`). Если у вас другой
   путь — либо поправьте `NavisworksInstallDir` в csproj, либо задайте
   переменную окружения `NAVISWORKS_2022_DIR`, либо соберите через
   `msbuild /p:NavisworksInstallDir="D:\Autodesk\Navisworks Manage 2022\"`.
3. Соберите конфигурацию `Release`. На выходе — `ClashIdFixer.dll`.

Собрать и проверить компиляцию в этой сессии было невозможно — рядом нет
установленного Navisworks и файлов Managed API. Весь код опирается на
реально подтверждённые (проверенные по документации/исходникам открытых
плагинов) элементы API, но два-три вспомогательных, не самых критичных
места намеренно сделаны через reflection с несколькими вариантами имён
(см. раздел «На что обратить внимание» ниже) — на случай, если точное имя
метода/свойства в вашей версии SDK отличается.

## Установка

Скопируйте `ClashIdFixer.dll` в папку плагинов Navisworks, например:

```
C:\ProgramData\Autodesk\ApplicationPlugins\...\Navisworks Manage 2022\Plugins\
```

или в `Plugins` внутри папки установки Navisworks (см. документацию
Autodesk по размещению .NET-плагинов для вашей версии). После запуска
Navisworks кнопка появится на вкладке **Add-ins** под названием
«Экспорт коллизий (исправленные Id)».

## Настройка

При первом запуске рядом с `ClashIdFixer.dll` автоматически создаётся файл
`ClashIdFixer.config.xml` (см. пример в
`src/ClashIdFixer/ClashIdFixer.config.sample.xml`) со значениями по
умолчанию. В нём можно поменять:

- `OutputFolder` — куда сохранять XML;
- `ObjectNodeTypes` — какие типы узлов считать «объектом»;
- `IdCandidates` — какие категории/свойства пробовать как Id;
- `HiddenSelectionSetName` — имя набора (Sets), который нужно скрыть перед
  пересчётом проверок («непроверяемые» элементы); пусто — шаг пропускается;
- `ShowAllBeforeExport` / `HideExcludedBeforeExport` / `UpdateTestsBeforeExport`
  — включение/отключение соответствующих обязательных шагов.

## Использование

1. Откройте документ, настройте видимость как обычно (плагин сам покажет
   всё и скроет набор «непроверяемых», если он задан в конфигурации).
2. Нажмите кнопку «Экспорт коллизий (исправленные Id)» на вкладке Add-ins.
3. Плагин выполнит все шаги по порядку и покажет сводку: сколько проверок,
   сколько коллизий, для скольких элементов удалось найти «правильный»
   объект. Путь к готовому XML будет показан в этом же окне.

## На что обратить внимание при первом запуске

Три вспомогательных места намеренно реализованы с запасными вариантами
имён через reflection, потому что их точные сигнатуры могут отличаться
между билдами SDK 2022, а проверить это здесь было не на чем:

- `ReflectionHelpers.GetModelFileName` — имя файла модели
  (`Model.SourceFileName` / `Model.FileName`);
- `ReflectionHelpers.TryRunTest` / `TryRunAllTests` — метод пересчёта
  проверки Clash Detective;
- `ModelPreparation.ResolveSelectionSetItems` — получение элементов
  именованного набора (explicit / search-set).

Если что-то из этого не находится (в сводке после экспорта появится
предупреждение, например «не удалось пересчитать проверки»), откройте
соответствующий файл в `src/ClashIdFixer/Core/`, посмотрите через
IntelliSense точное имя в вашей версии API и добавьте его в список
кандидатов (или замените заглушку на прямой вызов) — это точечное
исправление в одном месте, а не переделка логики.

Основная часть решения — поиск «правильного объекта» через
`LcOaNode/LcOaNodeIcon` и подмена Id — реализована напрямую, без
reflection, и является ядром задачи.
