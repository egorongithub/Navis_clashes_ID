# ClashIdFixer — исправление Id в XML-отчётах Clash Detective (Navisworks 2022)

## Проблема

В составных объектах Clash Detective находит коллизию на уровне
геометрии/подобъекта. В стандартный XML-отчёт попадают данные этого
подобъекта, а не самого объекта («правильный выбор» — уровень, у которого в
свойствах есть вкладка «Объект»). Плагин Signal выгружает параметры по
«правильному» выбору, поэтому связать отчёт о коллизиях с выгрузкой Signal
по ключу «имя файла + Id элемента» не получается — Id разные.

## Решение

Отчёт выгружается **стандартными средствами Clash Detective со всеми
настройками пользователя** (вкладка «Отчёт» → «Записать отчёт», формат XML).
Плагин ничего в этой выгрузке не изобретает — он берёт готовый XML и на
самом последнем этапе подменяет в нём значения подобъектов на значения их
составных объектов.

## Кнопка плагина (вкладка «BIM УП»)

Плагин добавляет собственную вкладку ленты **«BIM УП»** с кнопкой
**«Исправить ID в отчёте»** (иконка: синяя плашка «ID» с зелёной стрелкой
вверх). Запасная копия той же кнопки остаётся на вкладке Add-ins — на
случай, если на каком-то компьютере пользовательская вкладка не загрузится.

**Что делает кнопка**:

- выбираете стандартный XML-отчёт (диалог открывается в «Загрузках»);
- плагин по пути из отчёта (`<pathlink>`, с учётом узла-обёртки «Файл» и
  уровня NWD) находит каждый элемент коллизии в открытой модели;
- проверяет Id из отчёта (атрибут «ID объекта»): если он совпадает со
  свойством **«Объект» → «Id»** — не трогает;
- если не совпадает (значит в отчёт попал Id геометрии из «ID Объекта» →
  «Значение») — поднимается вверх по дереву выбора до первого узла, у
  которого есть свойство «Объект» → «Id», и записывает это значение в XML;
- сохраняет результат как `имя_отчёта_fixed.xml` в папку «Загрузки»
  (или в `OutputFolder` из настроек);
- показывает короткую сводку: исправлено / уже правильных / пропущено.
  Каждая пропущенная запись (путь не найден, элемент не опознан и т.п.)
  попадает строкой в отдельный файл `имя_отчёта_errors.txt` рядом с
  результатом — с именем конфликта, стороной, Id, причиной и путём.

Обработка идёт с окном прогресса, интерфейс не «зависает».

Единицы измерения определяются автоматически: масштаб между координатами
отчёта и API подбирается калибровкой по первым точкам коллизий (Revit-модели
обычно в футах, но плагин это не предполагает, а измеряет).

## Порядок работы

1. Открыть модель, настроить и обновить проверки в Clash Detective как
   обычно.
2. «Отчёт» → **«Записать отчёт»** (формат XML) → сохранить (например,
   в «Загрузки»).
3. Кнопка **«Исправить ID в отчёте (XML)»** → выбрать этот файл.
4. Забрать `..._fixed.xml` из «Загрузок» — в нём Id уже соответствуют
   «правильному выбору» и стыкуются с выгрузкой параметров Signal.

Важно: на шаге 3 должна быть открыта **та же модель**, по которой делался
отчёт, — элементы ищутся в текущем документе.

## Как выполняется подмена (техника)

- Элемент отчёта → `ModelItem` в модели: по цепочке `<pathlink>/<node>`.
  Точка привязки ищется по любому смещению (в отчёте путь начинается с
  узла-обёртки «Файл» и может включать уровень NWD-контейнера, которых нет
  среди корней открытого документа); дальше спуск строго по именам узлов,
  неоднозначные имена отслеживаются списком кандидатов.
- Выбор конкретного экземпляра среди одинаково названных соседей (путь по
  именам не уникален, а «ID объекта» вложенных семейств общий для всех
  экземпляров типа): берётся элемент, чей габаритный бокс ближе всего к
  **точке коллизии** из отчёта (`<clashpoint>`, с учётом единиц измерения
  отчёта). Id из отчёта дополнительно сверяется в пределах сегмента
  «геометрия → её элемент», не выше, чтобы общие узлы типа не давали ложных
  совпадений.
- Истинный Id: от выбранной геометрии вверх по родителям до первого узла,
  у которого есть свойство из настроек `TrueIdCategories` × `TrueIdProperties`
  (по умолчанию «Объект»/«Id», внутренне `LcRevitData_Element` /
  `LcRevitPropertyElementId`).
- Замена: в отчёте правятся только `<value>` атрибутов из
  `ReportIdAttributeNames` (по умолчанию «ID объекта»). Если Id из отчёта
  уже равен истинному Id какого-то кандидата — запись считается правильной
  и не трогается. Если элемент не удалось опознать однозначно — значение
  тоже не трогается (счётчик «не опознан» в сводке + подробности в
  `_diag.txt`). Больше ничего в отчёте не меняется.

## Сборка

Проект `.csproj` под .NET Framework 4.8, платформа x64.

1. Открыть `src/ClashIdFixer/ClashIdFixer.csproj` в Visual Studio 2019/2022.
2. Единственная зависимость — `Autodesk.Navisworks.Api.dll` из установки
   Navisworks 2022. Путь задаётся свойством `NavisworksInstallDir` в csproj
   (по умолчанию `C:\Program Files\Autodesk\Navisworks Manage 2022\`), либо
   переменной окружения `NAVISWORKS_2022_DIR`, либо параметром
   `msbuild /p:NavisworksInstallDir=...`.
3. Собрать **Release** → `bin\Release\ClashIdFixer.dll`.

## Установка

Скопировать `ClashIdFixer.dll` в
`C:\Program Files\Autodesk\Navisworks Manage 2022\Plugins\ClashIdFixer\` и
перезапустить Navisworks. Кнопка появится на вкладке **Add-ins**.

При обновлении со старой версии плагина удалите лежащий рядом с DLL старый
`ClashIdFixer.config.xml` — он пересоздастся с актуальными настройками.

## Настройка

`ClashIdFixer.config.xml` рядом с DLL (создаётся автоматически, образец —
`src/ClashIdFixer/ClashIdFixer.config.sample.xml`):

- `OutputFolder` — куда класть исправленный XML (пусто = «Загрузки»);
- `ReportIdAttributeNames` — имена атрибутов отчёта, значения которых
  проверяются/заменяются (по умолчанию «ID объекта»);
- `TrueIdCategories` / `TrueIdProperties` — где искать истинный Id
  (по умолчанию вкладка «Объект», графа «Id»).
